# SplitMate Phase 2 Supabase database plan

Phase 2 prepares cloud storage for authenticated SplitMate users. It does **not** modify the application code, migrate localStorage data, or perform synchronization yet.

## Files

- `SUPABASE_PHASE2_SCHEMA.sql` — idempotent schema, indexes, timestamp triggers, auth profile trigger, helper functions, grants, and RLS policies.
- Existing `localStorage` data remains untouched.

## Data model

### `profiles`
One row per `auth.users` record. Stores optional display information. The row is created by a trigger after a Supabase Auth user is created.

### `budgets`
Personal monthly budgets. `month_start` is normalized to the first day of the month and unique per user.

### `expenses`
Personal expenses owned by `user_id`. Amounts must be greater than zero and categories are restricted to the current SplitMate categories.

### `groups`
A group owned by `owner_id`. Group access is granted through `group_members`.

### `group_members`
The many-to-many relationship between authenticated users and groups. Members have either `admin` or `member` role. The group owner is treated as an administrator by the helper function even if an explicit membership row has not yet been inserted.

### `shared_expenses`
An expense associated with a group. It records the total, payer, creator, description, and date. Only group members can view it; the creator or group admin can delete it.

### `shared_expense_participants`
Participants and their equal or custom owed amount for each shared expense. The application should validate that participant amounts add up to the shared expense total before writing. The database currently enforces non-negative participant amounts; a later database function/trigger can enforce exact sum equality if desired.

### `settlements`
A payment from `from_user_id` to `to_user_id` within a group. `settled_at IS NULL` means pending. Only completed settlements affect balances.

## Access-control model

- Unauthenticated users receive no table privileges.
- Authenticated users can read and modify only their own `profiles`, `budgets`, and `expenses`.
- Group rows are visible to the owner and group members.
- Group owners/admins manage membership. Regular members cannot add, remove, or change members.
- Group members can read shared expenses, participants, and settlements for their groups.
- Shared-expense creators and group admins can delete shared expenses.
- Settlement creators and group admins can update/delete settlements. Group members can create settlements.
- `SECURITY DEFINER` helper functions use a fixed `search_path` and are granted only to `authenticated`, preventing recursive RLS evaluation on `group_members`.

## Important write-order detail

When creating a group from the browser:

1. Insert the `groups` row with `owner_id = auth.uid()`.
2. Insert an owner row into `group_members` with `role = 'admin'`.
3. Insert additional member rows only for users who have authenticated accounts and whose UUIDs are known.

For a shared expense:

1. Confirm the current user and payer are members of the target group.
2. Insert `shared_expenses` with `created_by_user_id = auth.uid()`.
3. Insert participant rows with `amount_owed >= 0`.
4. Validate that the participant amount total equals `total_amount` in application code until a server-side RPC/trigger is added.

## Balance calculation

For each group member:

```text
net balance =
  amount paid
  - amount owed
  + completed incoming settlements
  - completed outgoing settlements
```

In this schema:

- `amount paid` comes from `shared_expenses.total_amount` where the member is `paid_by_user_id`.
- `amount owed` comes from `shared_expense_participants.amount_owed`.
- A completed settlement is a row where `settled_at IS NOT NULL`.
- An incoming settlement is where `to_user_id` is the member.
- An outgoing settlement is where `from_user_id` is the member.
- Pending settlements (`settled_at IS NULL`) are excluded entirely.

A positive net balance means the member should receive money. A negative balance means the member owes money. Suggested transfers can be generated by matching negative balances to positive balances.

## Running the migration safely

1. Back up the Supabase project if it already contains important data.
2. Open Supabase Dashboard → SQL Editor.
3. Paste `SUPABASE_PHASE2_SCHEMA.sql`.
4. Review it before running.
5. Run it once. The script creates new tables and policies and does not contain `drop table`, `truncate`, or destructive data deletion.
6. Confirm that all eight tables have RLS enabled in Database → Tables.
7. Do not place a database password, service-role key, secret key, or management token in GitHub or frontend code.

The `drop policy` and `drop trigger` statements only replace same-named migration objects so the file can be safely re-run; they do not delete table data.

## Phase 2 is not application synchronization yet

Do not connect `script.js` to these tables until:

- the schema has been reviewed and applied;
- test users and test groups have been created;
- RLS has been tested with two separate authenticated accounts;
- local-to-cloud conflict and migration behavior has been designed;
- cloud errors and offline behavior have been specified.

The current SplitMate localStorage implementation remains the active data path.

## Security review notes

- The SQL never uses or asks for a service-role credential.
- RLS is enabled on every user-data table.
- The helper functions are `SECURITY DEFINER`, have `search_path = public`, and are not executable by `anon` or `public`.
- The public `authenticated` role receives table privileges, but RLS limits rows and operations.
- `paid_by_user_id`, settlement endpoints, and participant users are UUIDs referencing authenticated users, so Phase 2 should not use free-form names for cloud identity.
- Participant sum equality is intentionally left for a future RPC/trigger because inserting a shared expense and its participants is a multi-step operation. The client must not be trusted as the final integrity boundary for that rule.
